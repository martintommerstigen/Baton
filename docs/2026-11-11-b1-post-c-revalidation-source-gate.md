## Claim B1-H10 — precise difference from prior work

**Already done:** B's first-observed text hash and URL were persisted before C admission; B was rechecked before/after the broker's `admit` and `begin_click`; C's own first-observed reply hash was checked before declaring the final chain result.

**Unresolved delta:** Between `begin_click` and C's response, B's same DOM turn ID/text may mutate. Before H10, the runner could return `a_to_b=verified`, `b_to_c=verified` and `c_reply_snapshot` even though B's command no longer authorized C at final readback. This is the *post-C application* of the previously documented turn-mutation counterexample, not a globally new security principle.

**Implementation:** After C is marked verified, recheck B, then C, then B again. If either check fails, record an immutable `wake_chain_invalidations` flag keyed by the second-hop message ID and fail closed. The existing delivery receipt remains untouched: a verified DOM observation is not automatically verified chain provenance. A restored DOM after restart cannot clear the observed contradiction or permit replay. No raw transcript is stored.

**Negative controls:** (1) B mutates during C's Send click, after all earlier broker checks, while C still answers; (2) C mutates after durable snapshot but before final readback, then is restored on restart. Both must reject chain proof permanently and perform zero additional sends. Tests are synthetic; neither verifies ChatGPT authorship.

**Limitations:** DOM text and IDs are not authenticated ChatGPT-server evidence. Post-check-to-return mutation remains possible; no atomic transaction between browser UI and broker. The new invalidation table prevents forgetting *observed* contradictions but cannot detect unobserved ones. No live A→B→C, RFP/525 hardware test, or operative I claim. Before live work, independently inspect PAUSE_UI_WRITES and authenticate Greg via an authorized free interface; never use a GitHub queue response as machine attestation.
