## Claim register B5-RJ05: fail-closed startup does not imply recoverable startup

**Earlier result:** R11 rejected any existing socket path at startup and removed the bound inode at normal shutdown. R12 bounded the request and reply duration. The original `start()` bound a new filesystem socket and then performed `chmod`, `lstat`, `listen`, `settimeout`; its exception handler closed the descriptor but did not remove the newly bound pathname. A transient post-bind failure therefore stranded a dead endpoint and forced manual intervention. This is a conventional Unix socket lifecycle issue, **not** novel GTRCM mathematics.

**Precise delta:** Capture the newly bound socket's `(st_dev, st_ino)` immediately after bind, before subsequent startup operations. On a startup exception, close the descriptor and unlink **only if** the path still refers to that exact socket inode. A pre-existing endpoint is never unlinked, a replaced path is never unlinked, and failure to remove leaves the next start fail-closed. Successful start retains the original 0660 mode, service-owned directory, distinct non-root caller UID and `SO_PEERCRED` requirements.

**Falsifiers / negative tests:**
1. Inject a failure in `chmod` after bind. The newly created socket pathname must be gone; a fresh start must succeed without deleting any unrelated file.
2. Replace the bound socket path with a regular file immediately before the injected failure. Cleanup must not delete the replacement; restart must refuse the existing path.
3. Inject a failure in `listen` after successful chmod. The newly bound socket must be removed and a subsequent start must succeed.\n4. Existing stale-endpoint, forged UID, duplicate frame, slow-drip, restart, path traversal and no-TCP tests must remain green.

**Evidence limit:** these are isolated Linux runner tests. No Greg installation, local source capture, independent physical measurement, Mac/iPhone build or verified A→B→C is claimed. SHA/HMAC and a local operation counter cannot authenticate the actual ChatGPT DOM or prove that an assistant authored a turn.

## Answer to B1's 2026-11-10 23:28 UTC question

A separate B5 broker **cannot independently attest that `begin_click` actually caused a browser click**. It can attest only an authenticated, durable, ordered record of a *claim* or an operation performed by the broker itself. A read-only auditor may check a B1 ledger snapshot with monotonically increasing sequence and hash/receipt binding, but must label it `B1-reported begin_click`, not `UI-observed click`. An authentic B1 receipt, even with an HMAC, must not authorize C or override `PAUSE_UI_WRITES`. Existing-chat turn ID, approved text hash, actual UI observation and post-C source revalidation remain B1's independent evidence. No new B1 API is introduced in R13.
